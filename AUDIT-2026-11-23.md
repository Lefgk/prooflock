## 3. Findings

### [M-1] A silent arbiter locks the escrow and the provider bond forever. **Fixed**

**Where:** `dispute` L244-252 / `resolve` L255-263. Once `status == Disputed`, only `resolve` (arbiter-only) can move funds; `accept`, `autoRelease` and `refund` all require other statuses.
**Impact:** If the arbiter loses its key, disappears, or simply never acts, both the client's escrow and the provider's bond stay in the contract permanently. Nobody can recover them, and there's no admin escape.
**PoC:** `test_poc_silentArbiterLocksFundsForever` passed on `main` (1,100 USDC still locked after 10 years).
**Fix:** new `DISPUTE_TIMEOUT = 30 days` and `resolveStaleDispute(id)`. Anyone can call it once `block.timestamp >= reviewDeadline + 30 days` while the job is still `Disputed`. It settles 50/50: the provider gets `amount/2` minus the snapshotted fee, the client gets the rest (the odd unit), and a posted bond goes back to the provider. The arbiter can still `resolve` at any time until someone settles. 50/50 was chosen over a full refund because the client picks the arbiter: a client-favouring fallback would reward naming an arbiter who never answers. No new storage, so the `Job` struct/ABI is unchanged. The web shows a "Settle 50/50" button on disputed jobs.
**Tests:** `test_M1_silentArbiterNoLongerLocksFunds`, `test_M1_arbiterStillResolvesBeforeOrAfterTimeoutUntilSettled`, `test_M1_staleOnlyForDisputed`, `testFuzz_M1_staleSplitConserves` (with fees 0-5% and with/without bond), invariant `invariant_staleDisputeAlwaysSettleable` (new handler action `resolveStale`).

### [L-1] A USDC-blacklisted party can freeze the other party's funds. Acknowledged
`_settle` pushes every leg in one transaction. If the provider is blacklisted after posting a bond and misses the deadline, `refund` reverts on the bond return, which also blocks the client's refund. If the provider is blacklisted after delivering, `autoRelease`/`accept` revert; with no arbiter the escrow is stuck. A blacklisted client symmetrically blocks paths that pay the client. It needs a Circle blacklist action, hence Low. Fix if wanted: pull payments (credit balances, `claim()`).

### [L-2] A blacklisted `feeRecipient` blocks fee-bearing settlements
Only once `feeBps > 0`. The owner can fix it with `setFeeRecipient`.

### [L-3] `jobsOf(provider)` can be spammed
Anyone can create 1-wei jobs naming any provider, so `jobsOf` grows without bound and the web list gets slow. View-only; no funds at risk.

### [I-1] The client chooses the arbiter
The client can name its own alt as arbiter, then `dispute` and `resolve(0, slashBond=true)` to take the work for free plus the bond. Providers must vet the arbiter before posting a bond or delivering. The UI should make that explicit. `arbiter != client/provider` only blocks the obvious case.

### [I-2] With no arbiter, release is automatic
By design (SPEC): a provider can deliver any non-zero hash and get paid after the review window. Clients wanting protection must name an arbiter.

### [I-3] A missed deadline returns the bond to the provider
The bond is only slashable through a dispute, so it gives no protection against non-delivery. By design; noted for the spec.

### [I-4] The owner can raise the fee (up to the 5% cap) just before a `createJob`
The fee is snapshotted per job and shown in `JobCreated`. Optionally add a `maxFeeBps` argument to `createJob`.

### [I-5] Agent ids are unverified labels
`clientAgentId` / `providerAgentId` aren't checked against the ERC-8004 registry. Display only.
